# Сборка утреннего списка на VPS

С 05.11.2026 утренний список собирается дважды: **на VPS сразу после индекса EDGAR (22:03 по Нью-Йорку)** и **полным пересчётом в ежедневной сборке
на GitHub** (внешний cron 03:25 UTC, на деле 22:25–23:25 ET; крон GitHub в этом репозитории опаздывал на 7 ч 46 мин). Первая даёт список раньше и не зависит
от GitHub, вторая считает всё заново и страхует первую. Расхождения видны и исправляются.

Ревизия данных 04.11.2026 (В1, В4): список нужен к открытию (MOO до 9:28 ET), но сбой одной сборки без второй оставлял его без письма и без страницы.

## Как устроено

```

             1. индекс EDGAR за день D опубликован?        нет — ждём 2 минуты (до 23:30 ET); праздник SEC — выход без тревоги
             2. git fetch --depth 1 ветки data (анонимно)   ~13 с, в $STATE/repo, дерево каждый раз чистое
             3. scripts/live.mjs                            формы дня D с SEC (около 820 подач, ~2 минуты)
             4. воркер /bars: SPY, IWM                      бары за D и открытия дня входа (Yahoo с Cloudflare, не с адреса VPS)
             5. compute --only-morning --plan               у каких бумаг дня нет бара D0 (и у каких строк прошедших дней — открытий)
             6. воркер /bars: эти бумаги                    бумаги без кэша — со всей историей (420 дней: 52-недельный максимум)
             7. compute --only-morning --builder vps        один файл morning.json
             8. PUT воркеру /morning                        панель и сторож читают GET /morning
             9. scripts/notify.mjs --sender vps             письмо, если в env VPS есть TELEGRAM_*; затем отметка в воркере
            10. дозапрос бара D0 (waitD0)                   события дня, которым Yahoo отдал ряд без бара D0, — каждые 2 минуты до сборки
                                                            GitHub (03:25 UTC); бар пришёл — шаг 7 заново, шаг 8 — если строки дня изменились
03:25 UTC  daily.yml (GitHub) — полный пересчёт, как раньше
             · scripts/crosscheck.mjs                       основной список VPS и GitHub за ту же дату: состав, скор, крупнейшая покупка → morning.crossCheck
```

В ветку `data` VPS ничего не пишет: его рабочая копия — одноразовая. Код на VPS обновляет только `install.sh` (`git pull --ff-only` в `/srv/dash/repo-840`).

### Что изменил аудит форм 17.11.2026

- **Шаг 3, формы дня.** Подача из индекса, по которой SEC ответила «нет файла», больше не считается снятой: она ложится в добор (повтор
  в конце прохода и в следующих попытках), день — `partial`. Снятой подача считается только у дня старше суток. Причина — ночь 06.11.2026:
  31 подача из 515 ответила 404, день был помечен полным.
- **Формы из журнала ленты.** `live.mjs --feed-dir` берёт подачу индекса из журнала ленты, если она разобрана той же ревизией разбора
  (`rev`), скачана целиком (`end`) и подана в день индекса; качаются только недостающие (в покрытии дня — `fromFeed`). Подачи, которые
  скачать не удалось, тоже берутся из журнала ленты (`feedFillPending`) — по тому же условию; на последней попытке строки целой
  записи другой ревизии разбора вливаются, но подача остаётся в доборе. Подачу, которой нет в ленте и по которой SEC раз за разом
  отвечает «нет файла», сборка не ждёт до 23:30, если таких подач не больше трёх, ответ повторился три прохода подряд и с первого
  прохода индекса прошло 25 минут: список уходит с покрытием `partial`. При всплеске таких ответов (06.11 — 31 подача) ждём до конца.
- **Шаги 4–6, перекачка закрытых баров.** Бары SPY и IWM сборка перекачивает всегда, а план докачки называет ещё и то, что в копии данных уже есть (`plan.fresh`): бар D0 у бумаг дня и открытие с закрытием дня входа у строк прошедших дней, чей день входа — D0. В обычную ночь последний прогон GitHub шёл до открытия рынка, бара D0 нет ни у кого, и запросов столько же, сколько было. После прогона GitHub в торговые часы бар в ветке data лежит недозакрытый: в ночь 17→18.11.2026 сервер посчитал по таким барам цену всех 14 строк списка и результаты 24 вчерашних сделок. Источник не ответил — повтор до последней попытки; на последней сборка идёт с барами из ветки data и пишет об этом в журнал. Ответ, который кончается раньше копии данных, последних баров не стирает: бары копии позже конца ответа остаются, если их не больше трёх, они не дальше недели от конца ответа и от дня сборки, стык согласован (close в последний день ответа совпадает с копией в пределах 1%, без скачка больше чем втрое), а adjclose переводится в базу ответа (`cachedTail` в `scripts/lib/prices.mjs`; то же правило — у ежедневного прогона GitHub). Перекачанными такие бумаги не считаются: повтор попытки просит их снова. Вечером 19.11.2026 Yahoo у ~30 бумаг не отдавал бар 19.11, записанный прогоном после закрытия, перекачка его стирала, и из списка выпали IRTC и MTDR. Такие бумаги журнал называет строкой «ответ источника кончается раньше данных у N бумаг».
- **Шаги 5–6, минимумы дня.** План докачки называет сделки дня без минимума в слое `reference/lows.csv.gz` (`plan.lows`, ключ — тикер
  формы и дата сделки); сборка просит бары с запасом в неделю до первой даты сделки и дописывает минимумы в свою копию слоя до расчёта.
  Без этого гейт «скидка к рынку» на сервере отсеивал покупки, прошедшие внутри дневного диапазона (12.11.2026: COHR и EQPT).
- **Резерв по ленте** включается на последней попытке не только при неопубликованном индексе, но и когда SEC не отвечает вовсе или шаг
  форм не удался. Выход при этом — с ошибкой (тревога): список доставлен, но не по индексу. Доступность индекса проверяется в каждой
  попытке, пока он не подтверждён (на последней — до трёх проб), а шаг форм на последней попытке идёт с бюджетом 8 минут и одним
  повтором запроса: до предела юнита (23:48) должны успеть бары, расчёт и отправка.
- **Сверка** (`crosscheck.mjs`) сравнивает состав, скор и крупнейшую покупку события (расхождение больше 1% — отличие).
- **Бумага без кэша цен** качается с глубиной до 01.12.2025: признак «иностранный эмитент» смотрит, торговалась ли бумага раньше 2026 года.

### Почему бары идут через воркер

- Yahoo с адреса VPS нельзя: часовой лимит адреса почти выбран живыми котировками 839 (около 84 запросов в час при потолке ~90), 429 получил бы 839.
- `api.nasdaq.com` для запросов без браузера закрыт: с VPS ответ `HTTP/2 INTERNAL_ERROR` приходит за 50 мс на честный User-Agent проекта, с ноутбука запрос
  висит (замер 05.11.2026). Подбирать заголовки под защиту не стали — это обход защиты от ботов.
- Воркер уже ходит в Yahoo с адресов Cloudflare (котировки). Новый маршрут `GET /bars` (токен приёма) отдаёт ответ Yahoo chart как есть, разбирает его тот же
  код, что и в ежедневной сборке (`parseYahooChart`).

### Режим `compute --only-morning`

Считает цены только тикеров последних дней подачи (покупки за 45 дней или с начала живого счётчика), пишет `morning.json` и завершается: ни ленты, ни бэктеста,
ни портфелей. Содержимое файла совпадает с тем, что даёт полный `compute` (кроме `builtAt`), проверено на данных 04.11.2026. Время: около 27 с на VPS (замер 05.11.2026),
память до 1,9 ГБ. `--plan файл.json` записывает, что докачать.

### D0 и «без цены»

Оборот и цена берутся с бара дня D0 — последнего торгового дня не позже даты подачи (календарь SPY). У бумаги без бара D0 цены и оборота нет, событие не попадает в список
и называется в `days[].unpriced`. На VPS бары D0 докачиваются через воркер; бумага, которой у Yahoo нет вовсе, остаётся «без цены» и в списке GitHub тоже.
Временный отказ воркера или Yahoo (429, сеть) — повтор через 2 минуты; на последней попытке (около 23:28 ET) список собирается как есть, остальное исправит полный пересчёт.

**Дозапрос бара D0 (с 22.11.2026).** Yahoo бывает отвечает рядом без бара дня: у дорогой или малоторгуемой бумаги бар появляется позже
(ночь на 14.11.2026 — BH-A), а 19.11 в 22:04–22:42 ET его не было у ~30 бумаг. Это не сбой, повтора попытки он не вызывал, и бумага
оставалась «без цены» до следующей ночи. Утром бот торгует пересечение списков сервера и GitHub, поэтому такую бумагу он не купит, даже
если GitHub, собранный позже, цену уже видел (жёлтое «поздняя цена» в журнале бота). Теперь список уходит как раньше: в 22:20 ET по
нему строится вечерний план бота. После этого события дня, которым не хватило цены (`unpriced`) и у которых Yahoo отдал ряд без бара
D0, переспрашиваются каждые 2 минуты. Пришёл бар — он вливается в копию данных вместе с минимумом дня, список пересобирается; если
строки дня изменились, список уходит в воркер заново, а отметка `done/<день>.json` получает поле `d0Late`. Утром бот берёт список
заново и строит план по нему. Бумагу, которой у Yahoo нет вовсе (`missing`), не ждём; бумага с оборотом ниже порога списка бар
получает, но список заново не отправляет. В `d0Late` — только бумаги, чьи строки списка изменились. Ответ воркера 409 (хранит
список новее) отправкой не считается: дальше сервер не отправляет.

Срок дозапроса — **ночная сборка GitHub** (внешний cron 03:25 UTC: 22:25 ET зимой, 23:25 ET летом), не позже `--until`. Бот
(`ibkr-bot-840`, `merge_lists`) берёт за основу более позднюю сборку и решает, «поздняя ли цена», по времени сборок: бумага есть только у
GitHub, а сервер собран раньше и отметил её без цены, — жёлтое предупреждение; сервер собран позже — красное расхождение и сбойный день
(код 8). Если бы сервер отправлял список после GitHub, такие бумаги становились бы красными, а потеря цены у GitHub пряталась бы под
жёлтым. Поэтому перед каждой повторной отправкой сервер ещё и смотрит страницу: есть на ней список GitHub за этот день (ручной прогон,
бэкфил) — заново не отправляет. Срок проверяется и внутри круга: после него список не пересобирается и не отправляется, даже если
круг начался за секунды до срока (в журнале — «срок … наступил до дозапроса / до пересборки / до отправки»). Список сервера остаётся
раньше GitHub. Зимой окно — около 20 минут после первой отправки; бары, пришедшие у Yahoo позже, ждут, как раньше, следующей ночи.

Чего дозапрос не лечит: сервер получил бар дозапросом, а сборка GitHub его не получила (Yahoo отдал бар серверу в 22:10–22:25 ET и
снова не отдал GitHub). Тогда бумага есть только в более раннем списке — у бота это «только в одном источнике»: красное
расхождение и код дня 8, хотя сделки те же (бот торгует пересечение списков, бумаги в нём нет). Лечится только правкой сверки в
боте (`merge_lists`), вне этого запроса. До дозапроса в такую ночь бумаги не было ни в одном списке.

Дозапроса нет с `--once` и `--dry-run`, а также когда письма идут с сервера (`TELEGRAM_*` в env): письмо уже ушло со списком без
бумаги, а сверка GitHub сравнивает свой список с тем, что лежит в воркере, — уточнения «список изменён» не было бы. Выключить без
правки кода — `--no-d0-wait` в `ExecStart` юнита и `daemon-reload`; это до следующей установки (`install.sh` ставит юнит из
репозитория), насовсем — флагом в `ops/insider840-morning/insider840-morning.service` или откатом. В журнале: «без бара D0 у N бумаг дня», «дозапрос K: бар D0 пришёл у …», «строки
списка дня не изменились», «список отправлен заново», «список GitHub за день уже собран — заново не отправляю», «бар D0 так и не пришёл
к ЧЧ:ММ ET у …», «дозапрос бара D0 после отправки не запускается: <причина>» (`--once`, `--no-d0-wait`, пробный прогон,
письма с сервера). Не переспрашиваются (как и до правки): бумага дня, у которой в копии данных уже есть бар D0 из прогона GitHub в
торговые часы, а Yahoo ответил без бара (бар остаётся недозакрытым); открытия дня входа у строк вчерашнего списка.

**Проверка D0 = день подачи.** Календарь D0 берётся по SPY, а у ветки data в 22:03 ET ряды только до D−1: пока бар D у SPY не догружен, цена ≥$5 и оборот считались бы на день раньше, чем в проверке
стратегии. Поэтому бар D у SPY и IWM докачивается первым шагом, а план докачки сверяет `d0` с днём подачи (`d0Verdict`): не сошлось — повтор через 2 минуты, на последней попытке идём с предупреждением. Если биржа в день D
не торговала (Страстная пятница при открытом SEC), D0 законно раньше D — для этого `lib/calendar.mjs` знает биржевые праздники (`isMarketClosed`; День Колумба и День ветеранов — биржа открыта, SEC закрыта).

## Лента на весь день

Второй, независимый путь к тем же подачам. Отдельный юнит `insider840-feed` (`ops/insider840-feed/`, пн–пт 06:00–22:00 ET) опрашивает ленту getcurrent
(`type=4&owner=only`, до 300 записей за такт, раз в 45 с, в основную сессию биржи — раз в 15 с, не чаще 2,5 запроса в секунду к SEC), качает и разбирает каждую новую подачу тем же `parseForm4Txt`, что и живой контур,
и пишет журнал `/var/lib/insider840-feed/ГГГГ-ММ-ДД.jsonl`: `seen` (номер, форма, **дата подачи** из «Filed:» описания записи, время ленты), `form` (разобранные строки P и S) и `stat`.
Перезапуск безопасен: замеченное и разобранное читается из журналов последних четырёх дней (первый такт дня не перекачивает вчерашние формы).
Окно 06:00–22:00 ET: подачи после 22:00 и до 06:00 лента не видит — для них есть индекс. Запись `form` несёт ревизию разбора (`rev`) и признак
полного файла (`end`). Запрос к SEC — 10 секунд и один повтор; сбой страницы ленты не отменяет скачивание уже замеченных форм; три несдающиеся
подряд формы — остаток очереди ждёт следующего такта. Лента не читается 15 минут (и не меньше трёх тактов подряд) — сборщик выходит с ошибкой:
тревога юнита и перезапуск через 30 секунд. Цикл «15 минут + 30 секунд» — не больше четырёх перезапусков в час при пределе юнита
`StartLimitBurst=6`, поэтому сборщик переживает сбой любой длины.

**В 22:03, после `live.mjs`** сборка скачивает индекс дня и сверяет номера подач с лентой (`reconcile`):

| | что значит | что делает сборка |
|---|---|---|
| `extra` — есть в ленте, нет в индексе | индекс неполон | строки подач добавляются в шард живого контура и попадают в список; в лог — «ВНИМАНИЕ» |
| `missing` — есть в индексе, нет в ленте | слепые зоны ленты: подачи до 06:00 и после 22:00, глубже трёх страниц, не дождались скачивания | считается, в список не влияет (`live.mjs` скачал их из индекса) |
| `unparsed` — замечена лентой, не скачана | файл ещё не отдавался | считается; индекс покрыл |

Итог — `state/feed.json` и `coverage.feed` в `morning.json`: `{ seen, parsed, indexed, extra, extraAcc (до 10), missing, unparsed, merged, from, at }`. Лента пуста (сборщик не работал) — сверки нет, сборка идёт по индексу.

**Индекса нет до последней попытки (около 23:28 ET).** Если лента накопила подачи дня, список собирается по ленте: в шард вливаются все подачи дня из журнала,
`coverage = { status: "not-published", collected: N, source: "feed", feed: {…} }`, в `morning.json` — `source: "feed"` (по индексу — `"index"`), в письме — строка «Список собран по ленте EDGAR:
индекс за день ещё не вышел, возможны неполные данные». Юнит при этом завершается **с ошибкой** (тревога `dash-alert`: с EDGAR что-то не так), список доставлен. Лента пуста — собрать нечем,
выход с ошибкой без списка. Ежедневная сборка на GitHub, когда индекс выйдет, пересчитает всё, а расхождение даст письмо-уточнение (`crossCheck`).

## Сигнал в торговые часы

Для контура B бота (`ibkr-bot-840`, раздел `[intraday]`): форма 4 с покупкой, принятая SEC в торговые часы, скор от 3, бумага от $30 млн —
покупка сразу, продажа на закрытии того же дня. Проверка рычага и схема — `audit-840-levers-2026-11-17` (`REPORT.md`, `B-ВНЕДРЕНИЕ.md`).
Скор считает панель, бот его только читает — как с утренним списком. Юниты — `ops/insider840-signals/`.

**Справочник D−1** (`insider840-signals-ref`, пн–пт 23:52 и 07:00 ET, `scripts/vps/intraday-ref.mjs`). Отдельный шаг, от сборки списка в
22:03 не зависит: своя копия ветки data в `/var/lib/insider840-signals/build`, вселенная — бумаги справочника SEC на биржах с кэшем цен,
оборотом от $20 млн и ценой от $4 (запас к порогам сигнала $30 млн и $5), бары вселенной — через воркер `/bars` с перекрытием 24 дня
(в ветке data свежий бар лежит только у половины таких бумаг), бар незакрытого дня не берётся. Затем `compute --only-morning
--intraday-ref`: справочник пишет сам compute своими функциями — закрытие и оборот на последнем закрытом баре (`asOf`), хвост из 14 баров
(номинальное закрытие, просадка, оборот — для сделок с датой в прошлые дни), минимумы дня, признак «другие единицы», вердикт иностранного
эмитента на день сигнала, рутинные владельцы месяца, последние покупки пар «владелец — эмитент» (регулярная серия), группы связанных
владельцев, покупки последних 30 дней (поправки 4/A, повторные и синхронные подачи). Файл — `ref/<день сигнала>.json`, 2–3 МБ.
Формы в копии данных должны быть разобраны по последний рабочий день SEC перед днём сигнала (`formsThrough` справочника): по ним
поправки 4/A, повторные и синхронные подачи дня сигнала находят исходные строки. Ветку data пишет только прогон GitHub; если он
опоздал, живой шард берётся из копии ночной сборки списка на этом же сервере (`/var/lib/insider840-morning/repo`), а нет свежих форм
и там — шаг повторяет попытки, на последней собирает как есть и выходит с ошибкой: день будет выключен (`off`, `stale_forms`).
Годный справочник на нужный день уже лежит — шаг выходит без работы; негодный (формы устарели, справочники иностранных эмитентов
не готовы) или неполный (источник цен ответил не по всей вселенной) утренний запуск в 07:00 пересобирает, работая не дольше 45 минут.
У утреннего запуска жёсткий срок: расчёт (`compute`, до 3 ГБ памяти) не начинается позже 08:05 ET, а начатый снимается в 08:15 —
иначе медленный источник цен сдвинул бы его на старт дня бота (08:20), приём списка (08:30) и постановку заявок. Не успел — выход с
ошибкой (тревога «840 · справочник для сигналов в торговые часы», строка «НЕ СОБРАНО (поздно)»); справочника на день нет — процесс
сигналов пишет `off` (`no_ref`). Если ночью лёг неполный справочник (`partial`), он остаётся в работе: сигналов меньше, ложных нет.

**Расчёт** (`insider840-signals`, пн–пт 09:25–16:05 ET, `scripts/vps/signal-watch.mjs`, `scripts/lib/intraday.mjs`). Процесс раз в
полторы секунды читает дописанное в журнал ленты и по формам с покупкой и сегодняшней датой подачи пересчитывает событие эмитента —
когда пачка форм такта ленты дочитана. Лента за такт сначала пишет записи `seen` по всем новым подачам, потом качает формы по одной;
пока есть замеченные и не скачанные подачи, событие ждёт (`FormGate`, `HOLD`): подача, замеченная больше 20 с назад и всё не
скачанная, ждать не заставляет, одно событие ждёт не дольше 30 с. Так три формы одной цены одного такта («синхронная подача») не
делятся «две и одна» и по первым сигнал не уходит (до 22.11.2026 событие считалось по прочитанной порции, а порция могла кончиться
посреди пачки). Чьи подачи качаются, по записи `seen` не узнать (лента EDGAR даёт запись и на эмитента, и на подавшего; совпадение
CIK с эмитентом — у 15–20% подач), поэтому ждёт любая незакрытая подача. Ожидание пишется в запись (`hold`, секунды; `holdCap` —
отпущено по потолку). На повторе журналов 05–16.11 (модель времени записи формы: 0,5 с на форму такта) ожидание — медиана 0 с, 90% —
2 с, максимум 5 с, по потолку — ни разу. Формы разных тактов, между которыми пачка успела дочитаться, считаются по мере прихода:
те же `applyGates` и `buildDayFull`, что у ночного списка, контекст — из справочника. Сети нет. Отличия от списка — только в
том, какая цена известна в момент сигнала: цена, оборот и просадка — по `asOf`; сделка, датированная днём сигнала, сверяется с тем же
последним баром (итоговую сверку цены формы с котировкой делает бот); порог оборота — $30 млн. Эмитента нет в справочнике (нет в
справочнике SEC, нет кэша цен, нет свежего бара, оборот ниже запаса) — сигнала нет. Иностранный эмитент — сигнала нет.

**Файл сигналов дня** — `/var/lib/insider840-signals/ГГГГ-ММ-ДД.jsonl`, каталог открыт на чтение (читает бот, пользователь `ib840`).
Одна запись JSON в строке, файл только дописывается; строка без завершающего перевода строки — недописанная. Время — UTC.

| `k` | Когда | Главное |
|---|---|---|
| `run` | старт процесса | `ref`: `asOf`, `for`, `built`, `n` |
| `off` | сигналов сегодня не будет | `why`: `no_ref`, `stale_ref`, `bad_ref` (справочника нет, не на тот день, не читается), `fpi_warn` (справочники иностранных эмитентов не готовы), `stale_forms` (формы в справочнике старше последнего рабочего дня SEC); после неё записей `sig` не бывает, процесс выходит с кодом 3 |
| `sig` | событие получило скор от 2 | `cik`, `t`, `n` (1; 2 и дальше — только при росте скора), `acc` и `at` — подача, давшая этот скор, и время её приёма SEC; `at0` — самое раннее время приёма среди форм события; `atmx` — время приёма формы с крупнейшей покупкой (бот входит, только если свежа и она); `seen`, `tw` (момент записи — после дочитки пачки ленты); `score`, `pts`; `mx`, `val`, `rows`; `dv`, `px`, `dd`, `asOf`; `td`, `fpx`, `same`, `units` — для сверки цены формы с котировкой; необязательные `hold` (секунды ожидания пачки) и `holdCap` |
| `skip` | событие сигнала не дало | `why`: `no_ref_ticker`, `fpi`, `dv`, `px`, `score`, `amend`, `gates:<причины отсева>`; необязательные `hold`, `holdCap` |
| `stat` | раз в час и при тревоге | задержка «принято SEC → запись формы в журнале ленты»: `n`, `med`, `p90`, `ok90`, `alarm` |

Бот берёт только `sig` и сам проверяет порог скора (3), окно приёма 10:00–15:30, срок годности 15 минут от `at`, биржу, цену против
своей котировки, потолки.

**Лента в торговые часы.** Шаг опроса в основную сессию — 15 секунд (`--rth-interval`, `FEED.rthIntervalSec`), вне её — прежние 45.
Запись `form` журнала несёт два новых поля: `acs` — время приёма SEC с секундами, `w` — когда запись сделана; сборка списка их не
читает. Юнитам ленты и сигналов задан `CPUWeight=400`: в торговые часы процессор сервера занят фоновыми задачами.

**Тревога контура.** Медиана задержки за последний час торговых часов выше двух минут (не меньше пяти форм) — запись `stat` с
`alarm: true`, процесс выходит с ошибкой (тревога юнита) и перезапускается; не чаще раза в час. Сигнал старше 15 минут бот не
исполняет, поэтому такой день стоит пропущенных сигналов, а не убытков.

**Ограничения.** Эмитент, у которого в данных не было ни одной покупки инсайдера (нет кэша цен), сигнала не даст: 2–4% событий
2023–2026. У эмитента с двумя классами акций минимум дня ищется по тикеру формы: если его в слое нет, строка дешевле закрытия на 8%
отсеивается (ночная сборка докачивает такие минимумы после индекса) — сигнал может получить меньший скор, чем событие в утреннем списке.

## Что читает и пишет воркер

| Маршрут | Кто | Что |
|---|---|---|
| `PUT /morning` | VPS, токен | `morning.json`; версия старее хранимой (по `listFor`, затем `builtAt`) — 409; не JSON, нет `listFor`/`builtAt`/`builder`/`days`/`counter`, больше 4 МБ — 400/413 |
| `GET /morning` | панель, сторож, `crosscheck.mjs` | последний файл, `Cache-Control: no-store`, `Last-Modified` — момент записи; 404, пока нет |
| `PUT /morning/letter/ДАТА` | отправитель письма, токен | отметка «письмо за дату отправлено» `{by, at, ok}`; первая запись остаётся |
| `GET /morning/letter/ДАТА` | отправитель письма | отметка или 404 |
| `GET /bars?symbols=AAPL,BRK.B:2025-09-01&from=2026-10-01` | VPS, токен | ответ Yahoo chart по тикерам (до 25 за вызов; после двоеточия — своя дата начала) |

Токен — секрет воркера `PAPER_TOKEN` (имя осталось от закрытой вечерней схемы, бакет `radar840-paper`): на каждый бакет R2 один секрет записи, новых нет.

## Сводка бота для страницы

Блок страницы «Бот: что дал каждый контур» показывает факт живого счёта бота `ib840` раздельно по основному правилу и контуру B (методика — `docs/ЧТО-РАБОТАЕТ.md`). Канал:

```
бот ib840: ib840 public-split (юнит ib840-public, 17:05 и 21:40 ET)  →  /var/lib/ib840-public/split.json (0644, каталог 0755)
ночная сборка списка (22:03 ET): файл → белый список полей → блок bot в тексте, отправляемом PUT /morning  →  воркер  →  страница
```

- **Что в файле бота:** число сделок, на сделку — до комиссий, комиссии и после комиссий, сумма долей после комиссий по группам (основное правило с ногой хеджа, контур B по правилу, контур B приёмки, итог), даты первого и последнего живого дня, режим контура, сигналы, заявки и исполнение. Сумм счёта, тикеров и номеров нет.
- **Белый список** (`web/botsplit.js`, `cleanBotSplit`): в список уходят только перечисленные там поля и только числа, даты и режим; лишнее отбрасывается; поле не того вида, дата не строкой, время сборки из будущего или не сходящиеся между собой числа (сумма группы против «число × среднее», «после комиссий» против «до комиссий минус комиссии», итог против суммы групп, исполнено больше поставленного) снимают блок целиком. Страница проверяет сводку тем же кодом ещё раз; сбой блока на странице таблицу дня не трогает.
- **Список не меняется** (`scripts/lib/botsplit.mjs`): блок вставляется перед последней скобкой отправляемого текста, остальные байты те же; результат разбирается и сверяется со списком. Файла нет, на его месте не обычный файл, он не читается, не прошёл проверку, старше 10 дней или больше 16 КБ — список уходит без блока, в журнале юнита строка с причиной; сбоем сборки это не считается. Файл `site/data/morning.json` на сервере остаётся без блока.
- **Воркер не принял список с блоком** (ответ 400 или 413) — сборка тут же отправляет файл списка как есть, без блока (`sendMorning`); остальные отказы воркера — сбой попытки, как раньше.
- **Ключ и переменная:** `--bot-split файл` или `BOT_SPLIT_FILE` в env сборки; по умолчанию `/var/lib/ib840-public/split.json`. Воркер не менялся: `PUT /morning` проверяет обязательные поля списка и хранит текст как есть.
- **Страница** берёт сводку из любого ответа, где она есть (на деле — из воркера), даже когда сам список показывает со своей копии; копия страницы (`data/morning.json`, сборка GitHub) блока не несёт.

## Панель

Читает `morning.json` с обеих сторон — со страницы (GitHub) и из воркера (VPS) — и показывает **свежее**: по `listFor`, при равенстве по `builtAt` (полный пересчёт позже
VPS и побеждает). Любая сторона может не ответить. Контракт сторожа (репозиторий 839): `GET …/morning` → `listFor`, `builtAt`, `builder`, `coverage`; запасной — `…/data/morning.json`.
Воркер хранит только списки VPS: при остановке VPS его `listFor` отстаёт, и сторожу нужно сравнивать обе стороны, как панели.

## Письмо

Одно на дату подачи. VPS отправляет первым, если в его env есть `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`; иначе только собирает и публикует, и письмо шлёт GitHub, как раньше.
Дубль исключают три вещи: ключи `state/notify.json` ветки data (VPS их видит), отметка в воркере (GitHub читает её перед отправкой) и идемпотентность отметки.
Воркер недоступен — письмо уходит: пропущенное хуже редкого дубля. Если полный пересчёт разошёлся со списком VPS по составу или скору основного списка, а письмо отправил VPS,
уходит короткое «🔁 список уточнён» (ключ `fix|ДАТА`, раз на дату) со строками «+ добавлена», «− убрана», «≈ скор изменился».

## Проверка

Замеры на VPS (`claude@`, временный каталог, 05.11.2026): загрузка ветки data 11,6 с (повтор без изменений 0,7 с; ~184 МБ в `.git` и 198 МБ дерево),
`live.mjs` по одному дню — до дедупликации подач у соседа 1 723 запроса за 247 с (7 в секунду, 179 МБ); после неё качается одна подача на номер (820 уникальных за 03.11), то есть около двух минут; `compute --only-morning` — 27 с и 1,9 ГБ; весь цикл — около 5 минут от появления индекса.
На прошлых днях (`replay.mjs`, 23.10–03.11, восемь дней): строк списка 54 из 54 совпали с эталоном, результатов предыдущего дня 42 из 42, без цены — как в эталоне.
Бары в этой проверке подставной воркер берёт из того же кэша, поэтому она проверяет цепочку (срез → докачка → слияние → сборка), а не различия источников.

- Самотест: `npm test` (воркер `/morning`, `/bars`, отметка, сквозная сборка против подставного воркера с проверкой совпадения с полным пересчётом, уведомления, сверка).
- Ночь после прогона GitHub в торговые часы: `node scripts/vps/replay.mjs --full DATA --days Д --stale DIR` — бары D0 и открытия за D0 не срезаются, а подкладываются из каталога DIR (копия ветки data с недозакрытыми барами); сборка обязана их перекачать и совпасть с эталоном.
- Прошлые дни: `node scripts/vps/replay.mjs --full DATA --days Д1,Д2…` — для каждого дня копия данных приводится к виду на 22:03 ET (формы позже убраны, бары D0 и открытия срезаны),
  сборка VPS идёт против подставного воркера с барами из полного кэша и сравнивается с эталоном (lean-compute с барами на месте): состав и скор списка, сумма, оборот, цена,
  издержки и результаты предыдущего дня.
- Окружение VPS: `node scripts/vps/probe.mjs --check` (SEC, ветка data, воркер `/morning`, токен, `/bars`, диск).
