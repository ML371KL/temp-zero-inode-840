# Настройка уведомлений и внешнего расписания

Два независимых действия. Первое — уведомления в Telegram (15 минут). Второе — внешний
триггер обновления (10 минут), он важнее: без него данные могут приходить с задержкой
до восьми часов (замер — в [РАСПИСАНИЕ.md](РАСПИСАНИЕ.md)).

---

# Часть 1. Telegram-уведомления

## Шаг 1. Создать бота и получить токен

1. Открыть в Telegram чат с **[@BotFather](https://t.me/BotFather)** (проверьте синюю
   галочку — фальшивых BotFather много).
2. Отправить `/newbot`.
3. На вопрос «How are we going to call it?» ввести любое отображаемое имя, например
   `Инсайдерский радар`.
4. На вопрос про username ввести уникальное имя, **обязательно заканчивающееся на `bot`**,
   например `insider_radar_840_bot`. Если занято — BotFather попросит другое.
5. В ответ придёт сообщение с токеном вида:

   ```
   8123456789:AAF-abcdefghijklmnopqrstuvwxyz1234567
   ```

   Это **`TELEGRAM_BOT_TOKEN`**. Скопируйте целиком, вместе с цифрами и двоеточием.

> Токен — это полный доступ к боту. Если он утечёт, отправьте BotFather `/revoke`.

## Шаг 2. Разрешить боту писать вам и узнать ID чата

Бот **не может** написать первым — пока вы сами не начнёте диалог, все отправки будут
падать с ошибкой `403: bot can't initiate conversation with a user`.

1. Найти своего бота по username (из шага 1) и нажать **Start** (или отправить `/start`).
2. Отправить ему любое сообщение, например `привет`.
3. Открыть в браузере, подставив свой токен:

   ```
   https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates
   ```

4. В ответе найти `"chat":{"id":123456789,...}`. Число `123456789` — это
   **`TELEGRAM_CHAT_ID`**.

   Если в ответе пусто (`{"ok":true,"result":[]}`) — сообщение боту не дошло, вернитесь
   к пункту 2. Ещё вариант: написать боту **[@userinfobot](https://t.me/userinfobot)**,
   он сразу пришлёт ваш числовой ID.

**Если хотите получать уведомления в канал или группу**, а не в личку:
добавьте бота в канал участником и сделайте **администратором** (без прав администратора
он не сможет отправлять сообщения), затем напишите в канал что-нибудь и снова откройте
`getUpdates` — ID канала будет отрицательным и начнётся на `-100`, например
`-1001234567890`. В `TELEGRAM_CHAT_ID` нужно записать его целиком, включая минус.

## Шаг 3. Положить секреты в репозиторий

1. Открыть [Settings → Secrets and variables → Actions](https://github.com/ML371KL/temp-zero-inode-840/settings/secrets/actions).
2. Нажать **New repository secret**.
3. Создать первый секрет:
   - **Name**: `TELEGRAM_BOT_TOKEN` (имя должно совпадать буква в букву, регистр важен)
   - **Secret**: токен из шага 1
   - **Add secret**
4. Повторить для второго:
   - **Name**: `TELEGRAM_CHAT_ID`
   - **Secret**: число из шага 2

После сохранения GitHub больше не покажет значения — только имена. Это нормально.

## Шаг 4. Проверить, что связка работает

1. Открыть [Actions → Проверка Telegram](https://github.com/ML371KL/temp-zero-inode-840/actions/workflows/notify-test.yml).
2. Нажать **Run workflow** → **Run workflow** (ветка `main`).
3. Через ~30 секунд в Telegram придёт сообщение «✅ Инсайдерский радар — связка с Telegram
   работает» с кнопкой на дашборд.

Если сообщение не пришло, откройте лог прогона — скрипт печатает конкретную причину:

| Сообщение в логе | Что не так |
|---|---|
| `не заданы TELEGRAM_BOT_TOKEN и/или TELEGRAM_CHAT_ID` | секрет не создан или имя написано иначе |
| `HTTP 401 … Unauthorized` | токен неверный или отозван |
| `HTTP 400 … chat not found` | неверный `TELEGRAM_CHAT_ID` |
| `HTTP 403 … bot can't initiate conversation` | вы не нажали Start у бота (шаг 2) |
| `HTTP 403 … bot is not a member` | бот не добавлен в канал или не администратор |
| `NEXUS не настроен` | нет переменной `NEXUS_EVENTS_URL` или секрета `NEXUS_INGEST_TOKEN` |
| `NEXUS HTTP 401` | токен ленты отозван или не совпадает с тем, что ждёт воркер |

## Зеркало в ленту NEXUS

Каждое сообщение, которое бот отправляет в Telegram, дублируется в приватную ленту
[хаба](https://nexus.financehub.workers.dev/) — блок LIVE EVENT STREAM. Это один и тот же
текст, только без разметки; кнопки в ленту не уезжают.

Канал best-effort: его отказ никогда не блокирует ни Telegram, ни ежедневную публикацию
радара, но в лог прогона теперь всегда пишется, чем закончилось зеркалирование
(`NEXUS: событие принято`, `NEXUS HTTP …` или `NEXUS не настроен`). Тестовое сообщение из
шага 4 проверяет **оба** канала сразу.

Локальный запуск `--preview` доедет до ленты только если в окружении заданы
`NEXUS_EVENTS_URL` и `NEXUS_INGEST_TOKEN`; без них письмо уйдёт в Telegram, а на хабе
не появится — в логе будет строчка «NEXUS не настроен».

## Что будет приходить

Ровно одно событие: **в рабочем наборе открылась новая позиция**. То есть инсайдер купил
не меньше чем на $50 тыс. в бумаге с оборотом от $3 млн в день, и цена на дату сделки была
не ниже 7% от 52-недельного максимума. Всё остальное не присылается: прежние поводы
(кластеры, крупные покупки, зоны агрегатного индикатора) не пережили проверку на истории —
подробности в [ЧТО-РАБОТАЕТ.md](ЧТО-РАБОТАЕТ.md).

Письмо выглядит так:

> 📈 **CVBF** — новая позиция
> *CVB Financial Corp*
>
> Покупатель: O Brien Raymond V III (директор)
> Куплено на $455 тыс. по $22.77
> На 2.1% ниже 52-недельного максимума, оборот $31 млн в день
> Сейчас $23.45 (+3.0% с подачи)
>
> 🗓 Подача 4 авг · вход до 18 сен · выход 3 ноя
>
> `[ Карточка CVBF ]` `[ Все позиции ]`

Что важно знать про эти письма:

- **Единица уведомления — позиция, а не форма.** Если в той же бумаге инсайдеры покупают
  ещё раз, пока позиция открыта, второго письма не будет: входить второй раз не нужно,
  срок выхода считается от первой покупки. Новое письмо по той же бумаге придёт только
  после того, как трёхмесячное окно закроется и появится новая покупка.
- **Несколько форм одного дня — одно письмо.** В строке «Покупатели» будет первый по дате
  и «и ещё N», сумма и цена — по всем покупкам позиции.
- **Дат в письме три**: подача (от неё считается всё), крайний срок входа (45 дней — дальше
  сигнала уже нет) и ориентир выхода (три месяца).
- **Если позиций сразу больше четырёх** (бывает после простоя), вместо карточек придёт одна
  сводка строками — чтобы не превращать чат в ленту.
- **В тихие недели писем нет вовсе.** Набор даёт около восьми сигналов в месяц, а в
  отдельные месяцы не даёт ни одного. Молчание бота — это не поломка.

Первый прогон после обновления скрипта молча запоминает текущие позиции и ничего не шлёт —
иначе в чат разом упала бы вся последняя неделя.

Посмотреть, как выглядит письмо, можно локально:

```bash
node scripts/notify.mjs --preview
```

`--preview` берёт последнюю позицию набора и отправляет её в чат как образец, **не трогая
состояние** — повторное письмо по ней потом всё равно придёт, когда позиция появится
по-настоящему. Есть ещё `--dry-run` (печатает письма в консоль вместо отправки) и
`--fresh-days N` (расширить окно после долгого простоя), но оба честно имитируют прогон и
**помечают позиции как отправленные** — запускайте их на копии каталога `data`, а не на рабочем.

# Часть 2. Внешний cron

## Зачем это нужно

Штатное расписание GitHub ненадёжно по двум причинам, обе замерены или задокументированы:

1. **Задержка.** Первый же плановый прогон в этом репозитории, назначенный на 03:40 UTC,
   фактически стартовал в 11:26 UTC — **опоздание 7 часов 46 минут**.
2. **Тихое отключение.** GitHub выключает расписания в репозиториях без активности
   60 дней, причём коммиты, которые делает сам workflow, активностью **не считаются**.
   То есть радар может замолчать именно потому, что исправно работал сам.

Внешний триггер решает и то, и другое.

## Шаг 1. Создать токен доступа GitHub

1. Открыть [Settings → Developer settings → Personal access tokens → Fine-grained tokens](https://github.com/settings/personal-access-tokens/new).
2. Заполнить:
   - **Token name**: `insider-radar-cron`
   - **Expiration**: максимально доступный срок (обычно 1 год). **Запишите дату
     истечения** — когда токен умрёт, обновления просто перестанут запускаться молча.
   - **Resource owner**: ваш аккаунт `ML371KL`
   - **Repository access**: **Only select repositories** → выбрать
     `temp-zero-inode-840`
3. Раскрыть **Repository permissions** и найти в списке **Actions**:
   выставить **Read and write**. Больше ничего не включать — этого достаточно
   для запуска workflow и ограничивает ущерб при утечке токена.

   > Обратите внимание: GitHub автоматически добавит `Metadata: Read-only` — так и должно быть.

4. **Generate token** и сразу скопировать значение (вида `github_pat_11ABC…`) — второй раз
   оно не покажется.

Существующий токен от панели 838 здесь **не подойдёт**: fine-grained токены привязаны к
конкретным репозиториям. Либо добавьте этот репозиторий в его область, либо создайте
отдельный (предпочтительнее — меньше связей).

## Шаг 2. Создать задание на cron-job.org

1. Зарегистрироваться на [cron-job.org](https://cron-job.org) (бесплатного тарифа хватает).
2. **Create cronjob**.
3. Вкладка **Common**:
   - **Title**: `Инсайдерский радар — обновление`
   - **URL**: 
     ```
     https://api.github.com/repos/ML371KL/temp-zero-inode-840/actions/workflows/daily.yml/dispatches
     ```
   - **Execution schedule**: выбрать **Custom** и задать:
     - Minutes: `25`
     - Hours: `3`
     - Days of month: каждый
     - Months: каждый
     - Days of week: **Tue, Wed, Thu, Fri, Sat** (вторник–суббота)
   - **Timezone**: обязательно выставить **UTC**. По умолчанию подставляется зона
     аккаунта, и тогда расписание уедет на несколько часов.

4. Вкладка **Advanced**:
   - **Request method**: `POST`
   - **Headers** — добавить четыре строки:

     | Ключ | Значение |
     |---|---|
     | `Accept` | `application/vnd.github+json` |
     | `Authorization` | `Bearer github_pat_ВАШ_ТОКЕН` |
     | `X-GitHub-Api-Version` | `2022-11-28` |
     | `Content-Type` | `application/json` |

     В `Authorization` слово `Bearer`, пробел, затем токен — именно так.
   - **Request body**:
     ```json
     {"ref":"main"}
     ```
   - **Treat redirects as success**: не нужно.
   - Включить **Notify me if the job fails** (уведомление на почту при неуспешном запросе).

5. **Create cronjob**.

## Шаг 3. Проверить

1. В списке заданий нажать на созданное, затем **Test run** (или **Run now**).
2. Ожидаемый ответ GitHub: **`204 No Content`** с пустым телом. Это успех — у этого
   эндпоинта нет тела ответа.
3. Открыть [журнал сборок](https://github.com/ML371KL/temp-zero-inode-840/actions) —
   в течение минуты появится прогон «Ежедневное обновление радара» с триггером
   `workflow_dispatch`.

Если ответ иной:

| Код | Причина |
|---|---|
| `401 Bad credentials` | токен неверный, истёк или скопирован не полностью |
| `403` / `Resource not accessible by personal access token` | у токена нет права **Actions: Read and write** либо не выбран этот репозиторий |
| `404` | опечатка в URL, либо токен не видит репозиторий (проверьте Repository access) |
| `422 Invalid request` | тело запроса не `{"ref":"main"}` или не задан `Content-Type` |

## Почему 03:25 UTC

Индекс EDGAR с подачами за день публикуется в 22:01–22:04 ET стабильно (замерено).
03:25 UTC — это 22:25 ET зимой и 23:25 ET летом, то есть через 20+ минут после публикации,
круглый год без правок на переход времени. Штатный крон GitHub на 03:40 UTC остаётся
страховкой; повторный прогон безвреден — операция идемпотентна.

## Что делать, если обновления всё же встанут

На самой странице сверху появится красная плашка «Данные EDGAR устарели» — она рисуется
браузером и потому работает даже когда сломан весь сборочный цикл. По ссылке в плашке
открывается журнал сборок с причиной. Дополнительно GitHub присылает письмо владельцу
репозитория при неуспешном прогоне, а cron-job.org — при неуспешном запросе.
